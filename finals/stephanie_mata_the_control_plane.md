Architectural Design (0.75 to 1 page): Design the relational database cluster tracking file metadata. Compare hash vs. range sharding and identify common hotspot causes.

For our distributed file‑sync system, the metadata control plane is the part of the system that keeps track of files, versions, folders, and permissions. Even though the actual file contents live in chunk storage, the metadata layer is what tells every device which version of a file is current and which chunks belong to it. Since the system needs to support many users, large shared folders, and devices that constantly go offline and reconnect, the metadata database has to scale horizontally instead of relying on a single machine so sharding is required. There are 2 ways to partition the metadata across shards. The first sharding option is range sharding, where data is divided by key ranges such as (user_id, folder_id, file_name). Range sharding is useful because it preserves locality. For example, listing a folder becomes a simple range scan, since all files under the same folder path are stored close together. However, a major downside of key range sharding is that it can easily create hotspots if there are a lot of writes to nearby keys. For instance, if the partition key is a timestamp, or if there is a massive bulk upload of files into a single directory, all the writes will end up going to the same shard. That specific shard will become overloaded with writes while the other nodes sit idle, creating a severe bottleneck. The second option is hash sharding, where a hash function is applied to the partition key, and each shard is assigned a range of hash values. Hashing is much better at evenly distributing the data because the hash randomizes the distribution. However, this method destroys the natural ordering of keys, making range queries (like listing all files in a directory) highly inefficient because the matching records are now scattered across all shards. Both approaches can suffer from hotspots, which occur when a disproportionate amount of traffic targets a specific key, range, or index. Common hot spots are read hotspots this is when many queries repeatedly reading the same row or small span create a read heavy hotspot. Another is write hotspots that occur when a high volume of writes is directed at the same key, range, or small portion of the keyspace. Another is an index hotspot this happens when writes target the tail of an index, typically because the indexed column is monotonically increasing (e.g. timestamp) causing all inserts to hit the same range at the tail of the index. Given these tradeoffs, our system will adopt a hybrid approach by hashing the folder_id to distribute top-level directories evenly across the cluster, while sorting by file_name within those hashes to allow efficient folder scans.To solve write hotspots such as a viral shared folder accessed by thousands of users  the system will append a random number to the end of the key. This artificially distributes writes across multiple shards, preventing any single range from becoming overloaded.







Rebalancing Strategy (0.75 to 1 page): Explain consistent hashing and virtual slots. Design a rebalancing strategy that limits user-visible disruption when adding new database nodes.

Adding or removing nodes must not cause large amounts of data movement or noticeable disruption to users. To achieve this, the system uses consistent hashing, a technique that maps keys and nodes onto a logical circular space known as the hash ring to minimize data movement during scaling. If we naively map keys to nodes using a simple modulo operation (hash(key) % N), adding a new node would force almost every key to move to a new node, crippling the system. Consistent hashing solves this problem by mapping both the data keys and the physical database nodes to the same circular hash ring. When a system needs to look up or store a key, it hashes the key to find its position on the ring and then walks clockwise until it encounters the first available database node. This design ensures that when a new database node is added, it only intercepts a fraction of the keys from its immediate clockwise neighbor, leaving the rest of the cluster completely unaffected. However, placing physical nodes directly onto the hash ring creates an uneven distribution of data because random hashing rarely distributes nodes at perfectly equal intervals. To prevent hotspots where a single server becomes overloaded with an unfair share of data the system needs to introduce virtual slots. Instead of mapping a physical machine to a single point on the ring, the system hashes each physical server multiple times using different identifiers to create many different virtual slots scattered uniformly across the circular space. Virtual slots also make rebalancing far less disruptive. When we add a new database node to the cluster, the system does not need to recalculate the hash for individual records or split existing shards. Instead, it simply reassigns a portion of the virtual slots from the existing nodes to the new node until the load is balanced. To limit user-visible disruption during this process, the reassignment happens asynchronously in the background. Transferring large amounts of metadata over the network takes time, so the old assignment of shards continues to serve all read and write requests while the data transfer is in progress. Furthermore, because automated rebalancing can cause cascading failures by overloading the network or falsely identifying busy nodes as dead, our strategy will be to keep a human in the loop. We will generate rebalancing plans automatically, but require administrator approval before execution to prevent operational surprises during peak traffic. 














Isolation & Anomalies (0.75 to 1 page): Discuss the anomalies allowed by snapshot isolation (like write skew) and why it matters for resolving concurrent changes to file permissions.


Snapshot Isolation is a widely used concurrency control protocol designed to provide high performance by allowing transactions to read data from a consistent, point-in-time snapshot of the database. Under snapshot isolation, a transaction never blocks a concurrent write operation during its read phase, and it successfully commits if no other concurrent transaction has modified the exact same data rows. While this protocol eliminates classic concurrency anomalies such as dirty reads, non-repeatable reads, and phantom reads, it permits a dangerous concurrency anomaly known as write skew. Write skew occurs when two concurrent transactions read the exact same data from a snapshot, make a decision based on that data, and then concurrently update different records. Since they write to different rows, the database does not detect a standard write-write conflict, and both transactions commit successfully. 
This matters directly for file‑permission updates. Consider a shared folder where two administrators each have the ability to modify access controls. Suppose the system enforces a rule that at least one admin must always retain write access to the folder. Under snapshot isolation, both admins might open their permission panels at the same time, each seeing that the other admin still has write access. Admin A revokes their own write permission, believing Admin B still has it and Admin B does the same because these updates modify different rows in the permissions table, snapshot isolation allows both transactions to commit. The result is a folder with no remaining write‑capable administrators, a state that violates the system’s invariants but was not prevented by the database. To mitigate these issues, the metadata control plane must enforce additional safeguards beyond just using snapshot isolation. One approach is before altering any user's permissions, the transaction must execute a SELECT … FOR UPDATE on the relevant permission rows. By forcing both concurrent transactions to acquire an exclusive lock on the exact same parent record, the database will correctly queue the operations, committing the first and aborting the second, strictly enforcing our security invariants.
